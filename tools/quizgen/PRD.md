## 2. 배경과 문제 정의

### 2.1 공모전 맥락

한국특허정보원 e스포츠 게임 개발 공모전에 17개 팀이 참가 중이다. 다수의 팀이 기관 업무(특허 심사, 신입 육성, 업무 퀴즈)를 게임에 직접 이식하는 접근을 취하면서, 재미와 의미가 반비례하는 공통 문제를 겪고 있다.

우리 팀(KIPlay)은 **허브 로비 + 모듈형 미니게임** 구조의 플랫폼 전략을 택했다. 문서 심사 기준 3순위 평가를 받았으며, 평가에 기록된 강점과 약점은 다음과 같다.

- **강점** — 일회성 이벤트가 아닌 지속 확장 가능한 사내 e스포츠 문화의 기반이라는 포지셔닝, 부서 간 사일로 해소, 전광판 리더보드를 통한 관전성
- **약점** — 플랫폼형 다중 미니게임은 구현 난도가 높아, **실제로 돌아가는 데모가 없으면 오히려 감점 위험이 크다**

### 2.2 해결하려는 문제

세 가지 문제를 동시에 푼다.

1. **플랫폼이 살아 있음을 증명할 방법이 없다.** 심사위원이 17개 팀 데모를 다 본 뒤 남는 질문은 "행사 끝나고도 쓸까?"이며, 대부분의 팀은 여기에 답이 없다.
2. **우리 미니게임들도 결국 업무 퀴즈라 재미가 없다.** 재미를 담당하는 게임이 별도로 필요하다.
3. **사내 공지와 지식재산 동향을 아무도 읽지 않는다.** 조직 입장의 실질 효용이 필요하다.

### 2.3 접근

12:55는 **재미를 담당하는 게임이 아니라, 플랫폼이 매주 살아 움직인다는 증거**로 설계한다. 게임 자체의 재미는 지식이 아니라 **집단 동시 탈락의 드라마**에서 나온다. 문제 내용은 재미의 원천이 아니라 탈락을 만드는 장치일 뿐이다.

구현하면서 이 원칙은 한 문장으로 구체화됐다 — **숫자로 보여주던 것을 전부 사람으로 바꾼다.** 생존자 수는 화면에 실제로 남아 있는 사람이고, 집계는 좌우로 갈라선 무리이고, 탈락은 올라가는 층에 타지 못하고 남겨지는 것이다.

### 5.2 문항 규칙

- 문항 수는 **최대 5문항**. 단 **생존자가 1명이 되면 문항이 남아 있어도 즉시 종료**한다 (5.4-A).
- 각 문항은 **응답 10초 + 정답 공개 6~9초** (생존자 수에 따라 가변, 5.4-A).
- 응답은 O 또는 X 중 하나. **미응답은 오답 처리**한다 (무응답으로 살아남는 것을 허용하지 않는다).
- 응답 제출 후 시간이 끝나기 전까지 **변경 가능**하다. 마지막 제출이 최종이다.
- 오답자는 정답 공개와 동시에 **즉시 탈락**한다.
- 생존자가 임계값 이상이면 응답 중 실시간으로 **O/X 선택 인원 분포**가 노출된다 (5.4-B). 다수를 따를지 소신을 지킬지의 눈치싸움이 여기서 발생한다.

**[v1.0 → v2.0] 응답 7초 → 10초.** 7초는 문제를 읽고, 남들이 어디로 가는지 보고, 마음을 정할 틈이 없었다. 10초로 늘려도 한 판이 2분 안쪽이라 5분 슬롯에 여유가 있다. `QUESTION_MS` 환경변수로 조절한다.

### 5.3 난이도 배분

전멸과 무탈락을 모두 방지하기 위해 5문항의 난이도를 고정 배분한다.

| 문항 | 난이도 | 목표 정답률 | 성격 |
|---|---|---|---|
| 1 | 쉬움 | 85% | 워밍업. 전원 생존에 가깝게 |
| 2 | 쉬움~중간 | 70% | |
| 3 | 중간 | 55% | |
| 4 | 어려움 | 40% | |
| 5 | 어려움 | 30% | 결승 |

문제 소재 구성은 **정통(특허법·지식재산 뉴스·사내 공지) 30% / 사내 가십·난센스 70%**를 유지한다. 지식 격차가 고착되면 신입과 비전문 부서가 조기 전멸해 참여 동기가 사라지기 때문이다.

봇(체험 모드)의 정답률이 이 목표 곡선과 일치하는지는 `node scripts/curve.js`로 실측한다.

### 5.4 부활권

- **입사 2년 미만** 직원에게 회차마다 **1개** 자동 지급.
- 자동 부활이 아니다. 탈락이 확정되는 순간 **4초 선택 창**이 뜨고 본인이 쓸지 말지 결정한다.
- 시간 내 미선택 시 **미사용으로 처리**하고 탈락을 확정한다.
- 부활 시 다음 문항부터 정상 참여한다.
- 부활권은 **서든데스에서는 사용할 수 없다**.
- 신입에게는 새싹 배지(🌱)가 표시되어, 끝까지 생존 시 자연스럽게 응원 대상이 된다.

**설계 근거** — 지식 문제는 구조적으로 고참에게 유리하다. 부활권은 특혜가 아니라 균형 장치다.

**[v1.0 → v2.0] 선택 창 3초 → 4초.** 긴장감은 유지하면서 오조작을 줄인다.

### 5.4-A 층 상승과 조기 종료

정답을 맞힌 쪽의 바닥이 갈라져 한 층 위로 올라간다. 오답자는 그 층에 남는다. 탈락을 떨어뜨리는 대신 **남겨두는** 방식이라 톤이 덜 잔인하면서 정서적으로는 더 아프다.

**한 명만 남으면 문항이 남아 있어도 즉시 종료한다.** 그래야 회차마다 우승 층이 달라져 "이번 주는 4층 챔피언"이 이야깃거리가 된다. 5문항을 끝까지 가면 챔피언은 늘 최고층이라 층수에 변별력이 없다.

층 환경은 1층 로비, 그 위로 사무실 → 심사실 → 서고 → 전산실이 순환한다. **옥상은 게임 층이 아니라 우승 전용 장면**이며, 승자는 몇 층에서 이겼든 옥상에서 도시를 내려다본다.

정답 공개 시간은 층 상승 연출과 중계 멘트가 끝나기 전에 게임이 넘어가지 않도록 생존자 수에 따라 조절한다. 인원이 적을수록 길게 본다 — 후반일수록 한 명 한 명이 중요해지기 때문이다.

| 생존자 | 정답 공개 |
|---|---|
| 100명 이상 | 6초 |
| 30~99명 | 7초 |
| 11~29명 | 8초 |
| 10명 이하 | 9초 |
| 0명 (전멸) | 5초 |

### 5.4-B 선택 공개 범위

생존자가 **30명 이상**이면 사람들이 O·X로 달려가는 것이 실시간으로 보인다. 남의 판단을 참고할 수 있고, 이 관망은 오프라인 OX 퀴즈의 원래 재미이므로 막지 않는다.

생존자가 **30명 미만**이면 방향을 감춘다. 머리 위에 "선택함" 표시만 켜지고 어느 쪽인지는 보이지 않으며, 정답 공개 순간에야 전원이 갈라진다. 초반은 시끄러운 군중이고 후반은 조용하고 외로워지는 구조다. 임계값은 `TALLY_FROM` 환경변수로 바꾼다.

**[v1.0 → v2.0] 임계값 100명 → 30명.** 100이면 1~2문항 만에 그 밑으로 떨어져서 사람들이 달려가는 간판 연출이 초반에만 보이고 나머지 내내 정지 화면이 된다. 30이면 마지막 한두 문항만 깜깜이가 되어 "외로운 결승"이라는 원래 의도는 살면서 군중이 갈라지는 장면은 게임 내내 볼 수 있다.

> 이 가리기는 **반드시 서버에서** 수행한다. 클라이언트에서만 숨기면 개발자도구로 노출된다. 상품이 걸린 이상 타협할 수 없다.

### 5.5 서든데스

5문항 종료(또는 조기 종료 조건 미충족) 후 생존자가 2명 이상이면 실행한다.

- **숫자 근접값 문제** 1개를 출제한다. 예: "지난주 우리 원 특허 출원 건수는?"
- 제한 시간 **20초**. 정답에 가장 가까운 값을 제출한 사람이 승리한다.
- 동일 오차가 발생하면 **제출 속도**로 가린다. 이때 판정 기준은 서버 수신 시각이 아니라 **클라이언트가 보고한 반응 시간**이다. 회선이 느린 참여자가 불이익을 받지 않게 하기 위함이다.
- 미제출자는 즉시 탈락 처리한다.
- 생존자가 0명이면 **직전 문항까지 생존했던 인원 전체**를 공동 준우승으로 처리하고 챔피언 없음으로 종료한다.

**[v1.0 → v2.0] 제한 시간 15초 → 20초.** 숫자를 떠올리고 입력할 시간이 필요하다.

### 5.6 VIP 이벤트 — "원장님을 이겨라"

- 시즌당 2~3회 실행한다. 임원(원장·실장)이 동일한 사번으로 참전한다. 명부의 `vip: true`로 지정한다.
- VIP는 화면과 전광판에서 **왕관 표시(👑)**로 구분되고, 전광판에 "원장님 생존 중" 상태가 실시간으로 노출된다.
- **VIP보다 오래 생존한 참여자 전원**이 커피 상품권 5매 추첨 대상이 된다.
- VIP가 조기 탈락해도 문제가 되지 않도록 설계한다. 굴욕적 연출을 금지하고, 탈락 후에는 **명예 관전자**로 전환되어 한마디 코멘트를 남길 수 있게 한다.

### 5.8 밸런스 장치

- 3회 연속 우승자는 다음 회차 **응답 시간이 1초 단축**된다.
- 개인 순위만큼 **스트릭**과 **부서 참여율**을 화면 전면에 배치한다. 우승 확률이 낮은 다수를 붙잡는 것은 결국 이 두 지표다.

### 6.2 핵심 화면 요구사항

**S1 로그인** — 사번 입력 한 필드. 숫자 키패드가 바로 뜨도록 `inputmode="numeric"`. 사번에서 이름·부서·입사연차를 조회해 확인 후 입장.

**S2 대기실** — 12:55:00까지 남은 시간을 **초 단위 카운트다운**으로 크게 표시. 실시간 참가자 수가 올라가는 것이 보여야 한다. 이 화면은 재미 요소인 동시에 **접속 스파이크를 5분에 걸쳐 분산시키는 부하 설계**다.

**S3 문항 진행** — 문항 텍스트는 모바일에서도 한눈에 들어와야 한다. 화면 하단 절반을 **O / X 두 개의 거대 버튼**이 양분한다. 상단에 타이머가 시각적으로 줄어들고, 임계값 이상이면 O/X 분포가 실시간 갱신된다. 엄지 한 손 조작으로 완결되어야 한다. 답안 도달 여부(서버 수신 확인)를 화면에 표시한다.

**S4 정답 공개** — 정답 측이 강조되고 오답 측이 그 층에 남는다. 생존자 감소가 군중 무대에서 사람으로 보인다. 정답 근거가 된 원문 링크를 함께 노출한다.

**S5 부활권** — 4초 카운트다운과 함께 사용/포기 선택. 긴장감이 이 화면의 목적이다.

**S6 탈락 / 관전** — 탈락은 명확하고 극적으로 알린다. 다만 탈락 후에도 남은 문항과 생존자 수를 계속 볼 수 있어야 한다. 여기서 이탈하면 관전자가 사라진다.

**S9 전광판** — **3m 거리 판독**이 절대 기준이다. 군중 무대가 주 무대이고, 우측에 본부별 생존자 실시간 정렬(선두 본부 앰버 강조), 하단에 중계 자막. VIP 생존 여부를 별도 배지로 표시한다. 개인 조작 요소는 없으나 **오디오 잠금 해제 버튼 1회 클릭**이 필요하다 (6.6).

**S10 운영자 콘솔** — 게임 시작, 다음 단계 강제 진행, 리셋. 조작 3클릭 이내. 시연 중 사고 시 복구 수단이다.

**S11 체험 모드** — 사람도 시간도 없이 혼자 전체 흐름을 확인한다. 역할(신입/일반/원장), 인원(20~450명), 대기실 길이를 골라 시작하면 빈자리를 봇이 채운다. 봇은 난이도별 목표 정답률(5.3)에 맞춰 응답하므로 집계 바, 생존자 감소 곡선, 탈락 피드, 서든데스가 실제 회차와 같은 모양으로 움직인다. 체험 중에는 상단 안내 띠로 실전과 구분하고, 결과 화면의 「한 판 더」로 반복한다.

### 6.3 군중 무대

Canvas 단일 레이어. 참여자를 전부 사람으로 그린다. 전광판이 주 무대이고 참여자 폰은 축소 모드로 상단에 배치한다.

**구도는 세로다.** 군중이 아래 중앙에서 위의 O·X 간판으로 달려간다.

**인원이 줄수록 사람이 사람다워진다.** 카메라가 가까워지면서 표현이 바뀐다. 연출이면서 동시에 성능 설계다 — 450명일 땐 점이라 싸고, 상세히 그릴 땐 인원이 적다.

| 남은 인원 | 표현 | 노출 |
|---|---|---|
| 300+ | 점 | — |
| 100~300 | 굵은 점 | — |
| 30~100 | 실루엣 | — |
| 10~30 | 실루엣 | 사번 |
| 3~10 | 상세 | 이름 + 부서 |
| 2 | 결승 대치 | 전체 |

**머리 위 배지** — 👑 왕관(VIP), 🌱 새싹(2년차 미만, 부활권 보유), ⚪ 흰 링(나). 사람이 6px보다 작아지면 배지를 그리지 않는다. 뭉개진 얼룩은 정보가 아니라 노이즈다.

**본부 6색** — 14개 부서를 각각 색으로 나누면 전광판에서 읽히지 않는다. 상위 조직 5개 + 기타로 묶어 6색을 쓴다. 부서명은 근접 LOD 구간에서 텍스트로 노출한다. 조직 이름과 색은 `data/employees.json`의 `divisions`·`departments`만 고치면 되고 코드 수정은 없다.

### 6.4 우승 연출 — 옥상과 엔딩 카드

우승 장면은 게임 화면 안에 끼워 넣지 않고 끊어서 보여준다. 두 단계다.

**옥상 장면** — 챔피언 혼자 크게 남고 나머지는 물러난다. 발밑에 빛과 그림자가 깔리고 아래로 도시 스카이라인이 보인다. 결과 패널은 화면을 덮지 않고 위쪽만 어둡게 해서 장면을 가리지 않는다. 옥상 배경은 실사 사진에서 **구도와 빛만 가져오고 팔레트 양자화 + 디더링**으로 게임 화면과 같은 세계에 넣는다(`roofimage.js`). 캔버스 비율이 화면마다 크게 다르므로(데스크톱 5.4:1 ~ 폰 1.36:1) 난간선 위치를 선언해 어떤 비율에서도 우승자가 난간 안쪽에 서도록 크롭한다. 이미지가 없으면 절차적 옥상으로 폴백한다. 스타일 실험은 `roof-lab.html`에서 한다.

**엔딩 카드 — 등록특허공보 표제부** — 이번 주 챔피언에게 특허를 내주는 형식이다. (54) 발명의 명칭 자리에 우승자가, (73) 특허권자 자리에 기관이 들어가고 마지막에 인주 도장이 찍힌다. 레이아웃과 INID 코드는 실제 등록특허공보 2건을 근거로 그대로 따랐고, 기관명은 현행(지식재산처)으로 찍는다. 공보는 인쇄물이므로 전환도 인쇄의 문법을 쓴다 — 종이가 깔리고, 괘선이 그어지고, 활자가 앉고, 도장이 찍힌다. 페이드는 쓰지 않는다.

### 6.5 중계

진행 상황을 자막으로 띄우고 동시에 읽는다(`commentary.js`). **자막이 먼저고 음성이 나중이다** — 소리가 안 나는 환경에서도 진행이 끊기면 안 되기 때문이다.

말하는 것: 문항 시작과 난이도 / 정답·탈락 인원·상승 층 / **룰이 바뀌는 지점**(선택 은닉 진입) / **10명 이하부터 본부별 판세** ("시스템 2명, 지능 2명, 경영 1명. 팽팽합니다.") / VIP 탈락, 결승 진입, 챔피언.

### 6.6 소리

음원 파일도 네트워크 요청도 없이 **전부 런타임 합성**한다(`sfx.js`). 징은 어긋난 배음을 여러 개 쌓고 각각 다른 속도로 감쇠시켜 만든다. 나레이션은 브라우저 내장 음성 합성(Web Speech)을 쓴다.

- **전광판은 첫 클릭이 필요하다.** 브라우저 자동재생 정책 때문이며, 준비 화면 버튼을 운영자가 회차 전에 한 번 누른다.
- 참여자 화면은 입장 시 자동으로 풀리고, 대기실 하단 토글로 끌 수 있다.
- 음성 합성의 알려진 함정 3종(음성 목록 비동기 로드, utterance GC로 인한 끊김, Chrome 장문 멈춤)은 `sfx.js`가 처리한다.

### 6.7 디자인 원칙

- **다크 아레나** — 심연에 가까운 인디고 블랙 바탕에 앰버 신호색. 시계·전광판·출발안내판의 세계관.
- **모든 숫자는 고정폭(tabular)** — 카운트다운과 인원수가 흔들리지 않아야 한다.
- **모션은 상태 변화에만 쓴다** — 장식적 애니메이션을 금지한다.
- **접근성** — `prefers-reduced-motion` 존중, 포커스 링 유지, 색상만으로 정답/오답을 구분하지 않는다(형태와 텍스트 병기).

## 7. 기술 아키텍처

### 7.1 설계 판단

이 게임은 실시간 액션이 아니라 **방송형 동기 게임**이다. 전원이 같은 문제를 동시에 받고, 10초 안에 한 글자를 보내고, 결과를 함께 받는다. 이 성질에서 다음 결정이 따라온다.

**결정 1 — WebSocket이 아니라 SSE + POST.** 양방향 실시간 채널이 필요 없다. 서버→클라이언트 방송은 SSE 단방향, 클라이언트→서버 답안은 평범한 HTTP POST. 구현이 단순해지고 시연 당일 실패 확률이 낮아진다.

**결정 2 — 서버리스가 아니라 상시 단일 프로세스.** 서버리스는 장시간 연결 유지에 부적합하고, 인메모리 상태가 인스턴스마다 갈라진다. Node 프로세스 하나를 상시 띄우는 편이 450명 규모에서 더 싸고 안정적이다.

**결정 3 — 스케일아웃하지 않는다.** 인스턴스를 늘리는 순간 세션 고정과 Redis 공유 상태가 필요해져 복잡도만 오른다. 450명은 단일 인스턴스가 정답이다.

**결정 4 — 서버가 권위를 가지고, 클라이언트는 렌더링만 한다.** 탈락 판정은 전부 서버가 하고 클라이언트는 결과를 그린다. 화면 효과가 상태를 결정하는 일이 없다.

**결정 5 — 답안은 재시도한다.** 네트워크 순간 장애로 답안이 유실되면 그 사람은 틀려서가 아니라 회선 때문에 탈락한다. 이 게임에서 가장 나쁜 버그이므로, 응답 창이 열려 있는 동안 재시도하고 도달 여부를 화면에 표시한다. 버튼이 눌린 것과 서버가 받은 것은 다르다.

**결정 6 — 끊긴 참여자는 정리한다.** 그러지 않으면 폰을 닫은 사람이 영구히 참가자로 집계되어 참여율 지표가 오염된다. 단 진행 중에는 정리하지 않는다. 재접속하면 생존 상태를 이어받아야 한다.

### 7.2 스택과 구조

| 계층 | 선택 | 근거 |
|---|---|---|
| 서버 | **Node.js 내장 모듈만** (`http`·`fs`·`crypto`) | 의존성 0. `npm install` 실패 리스크 제거 |
| 실시간 | **SSE** | 단방향 방송에 최적, 자동 재연결 내장 |
| 클라이언트 | **바닐라 HTML/CSS/JS + Canvas** | 빌드 스텝 없음 |
| 상태 | **인메모리** | 회차 중 상태는 전부 메모리 |
| 문제·명부 | **JSON 파일** | 파이프라인·SSO가 각각 대체할 자리 |

> **런타임 외부 요청 금지.** CDN 스크립트·웹폰트·원격 이미지·음원 파일을 일절 사용하지 않는다. 사내망 환경과 오프라인 시연 모두에서 동작해야 하기 때문이다.

public/
  index.html app.js    참여자 화면
  board.html board.js  전광판

  ending.js            엔딩 카드 — 등록특허공보 표제부
  roofimage.js         옥상 실사 배경 (팔레트 양자화·디더링·난간 정렬 크롭)

  style.css            디자인 시스템
scripts/
  e2e.js               게임 흐름 검증 (40항목)

### 7.3 상태 기계

```
idle ──start──> lobby ──▶ question(n) ──▶ reveal(n) ──▶ [revive] ──┐
                                    ▲                              │
                                    └── n < 5 && 생존자 ≥ 2 ───────┘
                                                    │ n = 5 또는 생존자 ≤ 1
                                                    ▼
                                        [sudden] ──▶ result ──reset──> idle
```

| 상태 | 지속 | 전이 조건 |
|---|---|---|
| `idle` | — | 운영자 시작 |
| `lobby` | 설정값 (기본 30초, 실전 5분) | 타이머 만료 또는 운영자 강제 |
| `question` | 10초 | 타이머 만료 |
| `reveal` | 6~9초 (생존자 수 가변) | 타이머 만료 |
| `revive` | 4초 | 대상자 존재 시에만 진입 |
| `sudden` | 20초 | 생존자 2명 이상일 때만 진입 |
| `result` | — | 운영자 리셋 |

| POST | `/api/answer` | `{token, qIndex, answer, rt}` | `{ok}` |
| POST | `/api/revive` | `{token, use}` | `{ok}` |
| POST | `/api/sudden` | `{token, value, rt}` | `{ok}` |

**전광판 / 운영**

| 메서드 | 경로 | 요청 | 응답 |
|---|---|---|---|
| GET | `/api/spectate` | — | SSE 스트림 (인증 불필요) |
| POST | `/api/admin/start` | `{key, lobbySec}` | `{ok}` |
| POST | `/api/admin/next` | `{key}` | `{ok}` |
| POST | `/api/admin/reset` | `{key}` | `{ok}` |

`rt`는 클라이언트가 측정한 반응 시간(ms)이다. 서든데스 동률 판정에 사용한다.

**SSE 이벤트** — `snapshot`(재접속 복구용 전체 상태), `lobby`, `question`, `tally`(1초 간격, 임계값 미만이면 방향 은닉), `reveal`(공개 순간 전원의 선택 포함), `revive`(대상자에게만), `sudden`, `result`.

### 7.5 부하 설계와 실측

450명 전원 접속을 가정한다. 주 1회 편성은 참여를 한 시점에 집중시키므로 모수 전체가 들어온다고 본다.

**스파이크 대응**
- 12:50 대기실 선오픈으로 접속을 5분간 분산한다. 무료 호스팅의 슬립 워밍업도 겸한다.
- 연결 끊김 시 클라이언트는 **0~3초 무작위 지연 후** 재접속한다 (thundering herd 방지).
- `tally` 브로드캐스트는 매 응답이 아니라 **1초 간격 집계**로 보낸다.
- 파일 디스크립터 한도(ulimit)를 4096 이상으로 설정한다.

**실측 결과** (`node scripts/load.js`, 동일 머신 — 서버 처리 능력의 상한)

| 항목 | 450명 | 900명 |
|---|---|---|
| 로그인 처리량 | 3,103 req/s | 1,508 req/s |
| SSE 연결 수립 | 450개 / 115ms | 900개 / 527ms |
| 문항 도달 지연 p50 / p95 | 13ms / 31ms | 87ms / 117ms |
| 답안 제출 실패 | 0 / 2,250건 | 0 / 4,500건 |
| 서버 메모리 (rss) | 106MB | 155MB |

정원 450명 기준 **2배까지 여유가 있다.** 병목은 서버가 아니라 실제 회선이 될 것이므로 사내망 실환경 리허설이 남은 과제다.

**공정성** — 응답 10초는 넉넉하므로 100ms 수준의 네트워크 지연은 결과에 영향을 주지 않는다. 서든데스 속도 판정만 클라이언트 보고 반응 시간을 사용한다.

### 7.6 배포와 공유

**서버리스에 올리면 안 된다.** 인메모리 상태·상시 SSE 연결 전제라, 서버리스에서는 토큰이 인스턴스마다 갈라지고 스트림이 실행 시간 제한에 끊긴다. Vercel 연동(`vercel.json`, `api/index.js`)은 소수 인원 데모용으로만 남긴다.

| 용도 | 방식 |
|---|---|
| 정기 회차 | **상시 프로세스 호스팅** — `render.yaml`로 Render 즉시 배포. Railway·Fly.io·사내 서버 동일 |
| 임시 테스트 링크 | `share.ps1` — 이 PC의 서버를 localhost.run SSH 터널로 노출. 설치·계정 불필요, 운영자 키 자동 생성, SSE 통과 14항목 자동 점검 |
| 같은 사무실 | 내부 IP 직접 접속 (`http://<내부IP>:12055`) |

> **Cloudflare Tunnel 금지.** 엣지가 SSE 본문을 버퍼링해 이벤트가 도착하지 않는다. 헤더는 200이라 겉보기엔 멀쩡해서 원인을 찾기 어렵다. 실측으로 확인했다.

### 7.7 인증과 부정 방지

| 항목 | MVP | 정식 |
|---|---|---|
| 인증 | 사번 + 명부 조회 | 사내 SSO 연동 |
| 세션 | 발급 토큰, 동시 세션 1개 제한 | 동일 + 기기 토큰 |
| 부정 시도 | 중복 로그인 차단 | 이상 패턴 로깅, 추첨은 사번 단위 집계 |

**사번 체계** — 사내 사번은 **5자리**다. 명부(`data/employees.json`)에 등록된 사번은 `joinYear`를 그대로 쓰고, 미등록 사번은 `idFormat` 규칙으로 입사연도를 추정한다. 기본값은 앞 2자리를 두 자리 입사연도로 해석한다(`26005` → 2026년 입사 → 부활권 지급). 이 덕분에 명부를 450명분 채우지 않고도 테스트가 된다. 순번제 사번이라면 `yearPrefix: 0`으로 바꾸고 `roster`를 인사 데이터로 채우면 되며 코드 수정은 없다. 연차는 부활권 지급을 가르는 유일한 입력이므로 정식 운영 전 인사 데이터 대조가 필요하다.

## 11. 미결 사항

### 11.1 문제 공급 파이프라인 (별도 논의)

MVP는 **`data/questions.json`에서 문제를 읽는 구조**다. 파이프라인은 이 스키마만 맞추면 그대로 연결된다.

```json
{
  "id": "q-2026-08-17-01",
  "text": "특허 출원 후 심사청구는 5년 이내에 해야 한다.",
  "answer": "O",
  "difficulty": "easy",
  "category": "patent-law",
  "source": { "title": "특허법 제59조", "url": "https://..." },
  "evidence": "심사청구는 출원일부터 3년 이내에 하여야 한다."
}
```

`evidence`(근거 원문 문장)가 없는 문항은 파이프라인 단계에서 폐기한다. 이것이 할루시네이션 차단의 핵심이다.

논의가 필요한 항목:
- 수집 소스 범위 (특허청 보도자료 / 지식재산 전문지 / 사내 게시판)
- 사내 게시판 크롤링 권한 및 개인정보 필터링 정책 — **보안 부서 사전 협의 필요**
- 과거 정답률 기반 난이도 자동 라벨링
- 담당자 검수 UI

### 11.2 확인 필요 사항

| 항목 | 심각도 | 내용 |
|---|---|---|
| **외부망 접속 가능 여부** | 높음 | 사내망 전용이면 12:55 시간대의 전제가 무너진다. 외부 식당에서 접속이 안 되면 시각을 11:30으로 되돌려야 한다. **현재 가장 시급한 확인 사항** |
| 사내망 실환경 부하 리허설 | 높음 | 로컬 실측은 통과. 실제 회선·Wi-Fi에서 1회 이상 필요 |
| 사내 게시판 크롤링 권한 | 높음 | 보안 부서 협의. 불가 시 공개 지식재산 뉴스만으로 동작하도록 대비 |
| 근무시간 게임 승인 | 중간 | 점심시간 마지막 5분이라 명분은 있으나 전사 도입 시 공식 승인 필요 |
| 상품 예산 | 중간 | 오프닝 시즌 집중 배정, 정규 시즌은 소액 + 시즌 시상 |
| 사내 모니터 사용 | 낮음 | 전광판 송출 위치와 권한 |
