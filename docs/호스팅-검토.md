# 호스팅 검토 — 왜 상시 프로세스여야 하는가

**작성 2026-08-28 · 대상 `server.js` (12:55 OX 서바이벌)**

---

## 한 줄 결론

게임 코드는 이미 **전원 동시 진행**으로 만들어져 있다. 문제는 코드가 아니라 **Vercel**이다.
서버리스가 프로세스를 여러 개로 쪼개면서 "모두가 같은 게임을 본다"는 전제를 깨고 있다.
상시 프로세스 호스팅(Render · 회사 서버)으로 옮기면 **코드 한 줄 고치지 않고** 해결된다.

| | 지금 (Vercel) | 상시 프로세스 (Render · 회사 서버) |
|---|---|---|
| 참가자가 같은 게임을 보는가 | **아니오** — 인스턴스마다 다른 게임 | 예 |
| 회차 중 상태가 유지되는가 | **아니오** — 인스턴스가 재활용되며 사라짐 | 예 |
| 450명 동시 접속 | 검증 불가 (갈라짐) | **검증 완료** (아래 실측) |
| 필요한 코드 변경 | — | **없음** (`node server.js`) |

---

## 1. 이 게임의 구조 — 칠판 하나

`server.js`에는 게임 상태 객체 `game`이 **하나만** 있다(`server.js` 상단 `const game = {...}`).
지금 몇 번 문항인지, 누가 살아 있는지, 집계가 몇 대 몇인지가 전부 그 하나에 적혀 있고,
접속한 전원이 SSE(`/api/stream`)로 그 하나를 실시간으로 본다.

> 칠판이 하나 있고 450명이 그 칠판을 같이 본다. 이것이 "실전 회차"의 정의다.

이 전제는 PRD 7.1에 명시돼 있고, `render.yaml` 첫 주석에도 같은 말이 적혀 있다.
**단일 상시 프로세스**가 이 설계의 하드 요구사항이다.

## 2. Vercel이 그 전제를 깨는 방식

Vercel의 `/api/*`는 서버리스 함수다. 요청이 몰리면 **인스턴스를 자동으로 늘리고**,
새 인스턴스는 **자기만의 새 `game` 객체**를 갖는다. 칠판을 나눠 쓰는 게 아니라 각자 꺼낸다.

### 측정 — 인스턴스 분열

배포된 `https://kiplay-ox.vercel.app/api/health`에 **동시에 12번** 요청했다.
응답의 `uptimeSec`(그 인스턴스가 살아 있던 시간)을 보면 몇 개의 서버가 답했는지 드러난다.

```
14s, 14s, 0s, 14s, 14s, 14s, 14s, 14s, 14s, 14s, 0s, 14s
           ↑                                    ↑
      방금 생긴 새 서버                    또 다른 새 서버
```

**요청 12번에 이미 서버가 3개로 갈라졌다.** 450명이면 훨씬 많이 갈라진다.
갈라진 서버끼리는 서로를 모르므로 —— 생존자 수가 어긋나고, 챔피언이 여러 명 나오고,
전광판에 안 잡히는 참가자가 생긴다.

### 측정 — 상태 증발

같은 엔드포인트를 몇 분 간격으로 두 번 확인했다.

```
1차 확인:  uptimeSec 348
2차 확인:  uptimeSec 0     ← 그 사이 서버가 버려지고 새로 시작됐다
```

회차 진행 중에 이 일이 일어나면 **게임이 통째로 사라진다.** 재현을 기다릴 필요도 없이 관측됐다.

### 왜 지금은 "되는 것처럼" 보이는가

한가할 때는 Vercel이 인스턴스 하나를 재사용한다. 혼자 눌러보면 대개 정상으로 보인다.
**여러 명이 같은 순간에 들어올 때만 깨진다** —— 즉 심사 시연과 실전 회차, 정확히 그 두 상황에서만.

## 3. 상시 프로세스에서의 실측 — 450명

병목이 코드에 있는지 확인했다. `scripts/load.js`가 450개 SSE 동시 연결을 만들고
회차를 끝까지 돌리며 브로드캐스트 지연과 메모리를 잰다.

```
node scripts/load.js 450
```

```
[1] 로그인          450명 성공 · 실패 0 · 175ms  (2571 req/s)
[2] SSE 동시 연결    450개 · 137ms  (12:54:59 몰림 재현)
[3] 게임 1회차       답안 제출 실패 0건
    문항 도달 지연   p50 20ms · p95 34ms · max 42ms  (표본 1800)
    서버 메모리      rss 90MB · heap 18.4MB

450명 규모 통과
```

**코드는 병목이 아니다.** 450명에 메모리 90MB, 전원 도달 p95 34ms.
부하 때문에 고쳐야 할 것은 없다.

### 회차 소요 (10문항 기준, 실측)

| 인원 | 소요 | 비고 |
|---|---|---|
| 300명 | 213초 | Q10에서 정확히 1명으로 수렴 |
| 450명 | 210초 (평균 2회) | Q10에 2~4명 → 서든데스 |
| 160명 전원 정답 (최악) | 221초 | 서든데스 160명 |

예산은 **6분(360초)**. e2e가 그 선을 지킨다.

## 4. 어디로 옮길 것인가

| 용도 | 권장 | 이유 |
|---|---|---|
| 심사 · 시연 · 소수 테스트 | **Render 무료** | 10분 작업. 지금 Vercel보다 확실히 낫다 |
| 전사 450명 정규전 | **Render 유료(월 $7) 또는 회사 서버** | 무료는 15분 놀면 잠들어 **12:50 자동 개장이 안 뜬다** |

메모리 90MB는 무료 플랜(512MB)에도 넉넉히 들어간다. 무료 플랜의 진짜 제약은 **잠드는 것**이다.
자는 동안 서버 안의 타이머도 멈추므로 정기 회차가 열리지 않는다.

### Render 이전 절차

저장소에 `render.yaml`이 있어 설정 입력 없이 올라간다.

1. [render.com](https://render.com) → **New → Blueprint**
2. 저장소 `ideaprism/KIPlay_OX` 선택 → `render.yaml`이 자동으로 읽힌다
3. `ADMIN_KEY`만 입력하고 배포 (`sync: false`라 대시보드에서만 넣는다)

빌드 단계도 의존성 설치도 없다(`buildCommand: ''`). 헬스체크는 `/api/health`.

### 환경변수

| 변수 | 기본값 | 비고 |
|---|---|---|
| `ADMIN_KEY` | `kipi` | **반드시 변경.** 이 키로 회차를 열고 닫는다 |
| `PORT` | 10000 | `render.yaml`이 이미 설정 |
| `AUTO_START` | (켜짐) | `0`이면 정기 회차 자동 개장을 끈다 |
| `GAME_DOW` / `GAME_HOUR` / `GAME_MINUTE` | 1 / 12 / 55 | 월요일 12:55 KST |
| `QUESTION_MS` | 10000 | 응답 시간 |
| `TALLY_FROM` | 30 | 이 인원 미만이면 집계를 끊는다 |

시각 계산은 KST 고정 오프셋(+9)이라 컨테이너 TZ가 UTC여도 그대로 맞는다.

### 무료 플랜을 쓸 경우의 대비

자는 동안 자동 개장이 안 뜨므로 셋 중 하나가 필요하다.

- **유료 플랜** —— 상시 가동. 이 설계와 유일하게 맞는 선택
- **외부 핑** —— cron-job.org 등에서 10분마다 `/api/health` 호출 (무료)
- **수동 워밍업** —— 12:40쯤 운영자가 직접 한 번 연다. 잊으면 회차가 날아간다

### 배포 후 점검

정적 파일만 열리는 것으로는 부족하다. 이 게임의 생명선은 SSE라, 중간 프록시가
응답을 버퍼링하면 화면이 통째로 멈춘다. 아래 스크립트가 실제 스트리밍까지 확인한다.

```
node scripts/tunnel-check.js https://<서비스>.onrender.com <운영키>
```

이어서 눈으로 확인할 것:

- `/api/health` → `bank.pool` 48, `roster` 21
- `/` 로그인 화면에 「특허 보기」와 게임 개요
- `/?screen=question` → 상단이 `Q 03 / 10`
- `/admin.html` → 새 키로 열리고 기본값 `kipi`로는 **안 열리는지**

### 옛 주소 정리

**두 주소가 동시에 살아 있으면 안 된다.** 참가자가 옛 링크로 들어가면 다른 게임에 접속하고
그 결과는 전광판에 뜨지 않는다. Render 확인 후 `kiplay-ox.vercel.app`은 삭제하거나
리다이렉트하고, 사내 공지·QR에 배포된 링크도 함께 갱신한다.

## 5. 호스팅과 무관한 남은 과제 — 체험 모드 격리

이건 어디로 옮겨도 그대로 남는다. **실전 회차를 돌리기 전에 처리해야 한다.**

### 현상

체험 모드도 실전과 **같은 `game` 객체 하나**를 쓴다. 결과는 두 가지다.

```
[1] A가 「혼자 체험해보기」를 누름 (봇 20명)
    A가 보는 화면 : phase=lobby demo=true round=1 참가자=22
    B가 보는 화면 : phase=lobby demo=true round=1 참가자=22
    → B는 아무것도 안 눌렀는데 A의 체험에 끌려 들어갔다

[2] A의 체험 진행 중 B도 체험을 누름
    서버 응답    : 200 (거부하지 않는다)
    A: round=1 → round=2, 문항 1번 → 0번
    → A의 회차가 리셋됐다. B의 체험이 덮어썼다
```

지금 방어는 `/api/demo/start`의 "실전 진행 중이면 거부" 하나뿐인데,
회차 직전 `idle` 상태에는 그 조건이 걸리지 않는다.
**12:54:50에 누군가 체험 버튼을 누르면 정기 회차가 통째로 리셋된다.**

### 선택지

| | 내용 | 작업량 | risk |
|---|---|---|---|
| **A. 방어만** | 정기 회차 앞뒤(12:40~13:10)와 다른 사람 체험 중에는 체험 시작 거부. 격리는 안 되지만 **회차가 날아가는 사고는 막힌다** | 10~20줄 | **낮음** |
| **B. 본인에게만 송출** | 체험 상태를 시작한 사람에게만 흘리고 나머지에겐 `idle`을 보낸다 | 20~40줄 (`pushState` 주변) | 중간 |
| **C. 룸 구조** | `game` 싱글턴 → 실전 1개 + 체험 N개 | `game.` 참조 **142줄 / 31개 함수**, 전역 타이머 2개 다중화 | **높음** |

C는 서버 전면 재작업이고 e2e 58항목이 싱글턴 구조를 전제로 짜여 있어 테스트도 함께 손봐야 한다.
**권장은 A** —— 실질적 위험(회차 증발)은 A가 전부 막는다. B는 체험이 실제로 자주 쓰이는 것이
확인된 뒤, C는 미니게임이 여러 개로 늘어 플랫폼이 될 때 한다.
