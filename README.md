포트와 운영 키는 환경변수로 바꾼다. `PORT=8080 ADMIN_KEY=비밀 node server.js`

## 혼자 체험해보기

**사람도 시간도 필요 없다.** 참여자 화면에서 **「혼자 체험해보기」**를 누르면 된다.

역할(신입 / 일반 / 스페셜 게스트), 함께할 인원(20~450명), 대기실 길이를 고르고 시작하면
빈자리를 봇이 채운다. 봇은 난이도별 목표 정답률(쉬움 85% · 보통 60% · 어려움 40%)에 맞춰
답하므로 집계 바, 생존자 감소 곡선, 탈락 피드, 서든데스가 실제 회차와 같은 모양으로 움직인다.

체험 중에는 화면 상단에 안내 띠가 떠서 실전 회차와 헷갈리지 않는다.
결과 화면의 **「한 판 더」**로 바로 다시 돌릴 수 있다.

역할별로 이런 것을 확인할 수 있다.

| 역할 | 볼 수 있는 것 |
|---|---|
| 🌱 신입 | 부활권 3초 선택 창. 쓸지 말지 고민하는 그 순간 |
| 일반 직원 | 표준 진행 |
| 👑 스페셜 게스트 | 소속 없이 참전. 왕관 표시, 전광판의 "스페셜 게스트 생존 중" |

봇 정답률이 목표와 맞는지는 `node scripts/curve.js`로 실측할 수 있다.

## 실전처럼 돌려보기

1. **운영자 화면**을 열어둔다. 기본 키는 `kipi`.
2. **참여자 화면**을 여러 탭(또는 여러 폰)에서 열고 사번으로 입장한다.
3. **전광판**을 큰 화면에 띄운다.
4. 운영자 화면에서 대기실 길이를 정하고 **게임 시작**을 누른다.

진행이 막히면 운영자 화면의 **다음 단계로**가 현재 단계를 즉시 끝낸다. 시연 중 복구 수단이다.

### 사번 체계

사번은 **5자리**다. 명부(`data/employees.json`)에 등록된 사번은 `joinYear` 값을 그대로 쓰고,
명부에 없는 사번은 `idFormat` 규칙으로 입사연도를 추정해 자동 등록한다.

```json
"idFormat": { "digits": 5, "yearPrefix": 2, "defaultYears": 5 }
```

기본값은 **앞 2자리를 두 자리 입사연도로 해석**한다. `26005`는 2026년 입사 5번이 되어
2년차 미만이므로 부활권 1개를 받는다. 이 덕분에 명부를 450명분 채우지 않아도
아무 5자리나 넣어 테스트할 수 있다.

> **사내 사번이 순번제라면** `yearPrefix`를 `0`으로 바꾸고 `roster`를 인사 데이터로 채우면 된다.
> 그 경우 미등록 사번은 `defaultYears` 연차로 처리되어 부활권 대상에서 빠진다.
> 이 파일만 고치면 되고 코드는 건드릴 필요가 없다.

### VIP 이벤트

명부에서 `vip: true`인 사번으로 입장하면 왕관이 붙고, 전광판에 "스페셜 게스트 생존 중"이
실시간 표시된다. 그보다 오래 살아남은 사람이 추첨 대상으로 집계된다.
기본 명부에는 `95001`(스페셜 게스트)이 들어 있다.

## 검증

```bash
node scripts/e2e.js
```

실제 HTTP/SSE로 플레이어를 붙여 게임을 끝까지 돌린다. 정상 진행, 부활권,
전멸 구제 후 서든데스, 체험 모드, 입력 검증까지 40개 항목. **현재 전부 통과.**

```bash
node scripts/load.js 450
```

450명 동시 접속 리허설. 12시 54분 59초의 접속 스파이크를 재현한다.

### 실측 결과

같은 머신에서 측정했으므로 네트워크 지연은 포함되지 않는다. 서버 처리 능력의 상한을 보는 수치다.

| 항목 | 450명 | 900명 |
|---|---|---|
| 로그인 처리량 | 3,103 req/s | 1,508 req/s |
| SSE 연결 수립 | 450개 / 115ms | 900개 / 527ms |
| 문항 도달 지연 p50 | 13ms | 87ms |
| 문항 도달 지연 p95 | 31ms | 117ms |
| 답안 제출 실패 | 0 / 2,250건 | 0 / 4,500건 |
| 서버 메모리 (rss) | 106MB | 155MB |

정원 450명 기준으로 **2배까지 여유가 있다.** 병목은 서버가 아니라 실제 회선이 될 것이므로,
사내망 실환경에서 한 번 더 리허설이 필요하다.

## 직원들에게 테스트 링크 보내기

배포 없이, 이 PC의 서버를 그대로 인터넷에 노출한다. 계정도 설치도 필요 없다.

```powershell
powershell -ExecutionPolicy Bypass -File share.ps1
```

공개 주소(`https://xxxx.lhr.life`)와 운영자 키가 창에 표시된다. 그 주소를 그대로 보내면 된다.
Windows에 기본 포함된 `ssh`로 [localhost.run](https://localhost.run)에 터널을 뚫는 방식이라
따로 설치할 게 없다. 스크립트가 서버 기동부터 연결 점검까지 하고, 마지막에 SSE 스트리밍이
실제로 통과하는지 14개 항목을 확인한 결과를 보여준다.

이미 떠 있는 주소를 점검만 하려면:

```bash
node scripts/tunnel-check.js https://xxxx.lhr.life 운영키
```

**알아둘 것**

- 이 PC가 켜져 있고 창이 떠 있는 동안만 살아 있다. **절전 모드로 들어가면 끊긴다.**
- URL은 껐다 켤 때마다 바뀐다.
- 운영자 키는 실행할 때마다 새로 만든다. **링크와 함께 뿌리지 말 것.**
- 정기 회차에는 이 방식 대신 아래 상시 호스팅에 올린다.

> **Cloudflare Tunnel은 쓰지 말 것.** `cloudflared`로도 주소는 나오지만 Cloudflare 엣지가
> SSE 본문을 붙잡아 이벤트가 하나도 도착하지 않는다. 헤더는 200으로 오기 때문에 겉보기엔
> 멀쩡한데 화면만 멈춰서 원인을 찾기 어렵다. 실측으로 확인한 사항이다.

### 같은 사무실이라면

터널도 필요 없다. 서버를 띄우고 이 PC의 내부 IP를 알려주면 된다.

```bash
node server.js
```

`http://<내부IP>:12055` 로 접속한다. 내부 IP는 `ipconfig`로 확인한다.
Windows 방화벽이 처음 한 번 물어보면 허용해야 한다. 사내망 안에서만 도는 방식이라
가장 빠르고 안정적이지만, 재택 중인 사람은 접속할 수 없다.

## 배포

**이 앱은 서버리스에 올리면 안 된다.** 인메모리 상태를 가진 단일 상시 프로세스를 전제로
설계했기 때문이다(PRD 7.1). 서버리스에서는 요청이 서로 다른 인스턴스로 흩어져서
한 인스턴스에서 발급한 토큰이 다른 인스턴스에서는 무효로 보이고, 운영자가 시작한 회차가
참여자에게 보이지 않는다. 장시간 SSE 연결도 실행 시간 제한에 걸려 끊긴다.

### 권장 — 상시 프로세스 호스팅

`render.yaml`이 들어 있으므로 Render는 설정 없이 바로 올라간다.

1. [render.com](https://render.com) → New → **Blueprint**
2. GitHub 저장소 `ideaprism/KIPlay_OX` 선택
3. `ADMIN_KEY`를 기본값(`kipi`)이 아닌 값으로 바꾸고 배포

Railway, Fly.io, 사내 서버도 동일하게 동작한다. 필요한 건 `node server.js`가
계속 떠 있는 환경 하나뿐이고, 빌드 단계도 의존성 설치도 없다.

> 무료 플랜은 15분 무활동 시 잠든다. 회차 시작 전에 미리 한 번 열어 깨워두거나
> 유료 플랜을 쓴다. 12시 50분 대기실 선오픈이 이 워밍업을 겸한다.

### Vercel

저장소가 Vercel 프로젝트 `kiplay-ox`에 연결되어 있고 `vercel.json`·`api/index.js`도 들어 있지만,
**위의 이유로 실제 회차용으로는 쓰지 않기를 권한다.** 소수 인원이 잠깐 눌러보는 정도는
동작할 수 있으나 인원이 늘면 인스턴스가 갈라지면서 예고 없이 깨진다.

## 화면

숫자로 보여주던 것을 전부 사람으로 바꿨다. 생존자 수는 화면에 실제로 남아 있는 사람이고,
집계는 좌우로 갈라선 무리이고, 탈락은 올라가는 층에 타지 못하고 남겨지는 것이다.

### 층을 올라간다

정답을 맞힌 쪽의 바닥이 갈라져 위로 올라간다. 틀린 쪽은 그 층에 남는다.
**한 명만 남으면 문항이 남았어도 거기서 끝나기 때문에** 회차마다 우승 층이 달라진다.
어려운 회차는 3층에서 끝나고 쉬운 회차는 6층까지 간다. "이번 주는 4층 챔피언"이 매주 다른 이야기가 된다.

| 층 | 환경 |
|---|---|
| 1층 | 로비 |
| 2층 이상 | 사무실 → 심사실 → 서고 → 전산실 순환 |
| 옥상 | 우승 전용. 층과 무관하게 승자는 옥상에서 도시를 내려다본다 |

우승 장면에서는 **챔피언 혼자 크게 남고 나머지는 물러난다.** 발밑에 빛과 그림자가 깔리고
아래로 도시 스카이라인이 보인다. 결과 패널은 화면을 덮지 않고 위쪽만 어둡게 해서
그 장면을 가리지 않는다.

### 머리 위 배지

| 표시 | 뜻 |
|---|---|
| 👑 왕관 | 임원(VIP) |
| 🌱 새싹 | 2년차 미만. 부활권 보유 |
| ⚪ 흰 링 | 나 |

사람이 6px보다 작아지면 배지를 그리지 않는다. 뭉개진 얼룩은 정보가 아니라 노이즈다.

### 인원이 줄수록 사람이 사람다워진다

카메라가 가까워지면서 표현이 바뀐다. 이건 연출이면서 동시에 성능 설계다.
450명일 땐 점이라 싸고, 상세히 그릴 땐 인원이 적다.

| 남은 인원 | 표현 | 노출 |
|---|---|---|
| 300+ | 점 | — |
| 100~300 | 굵은 점 | — |
| 30~100 | 실루엣 | — |
| 10~30 | 실루엣 | 사번 |
| 3~10 | 상세 | 이름 + 부서 |
| 2 | 결승 대치 | 전체 |

### 마지막 30명부터는 선택이 보이지 않는다

생존자가 **30명 이상**일 때는 사람들이 O·X로 달려가는 게 실시간으로 보인다. 눈치를 볼 수 있다.
30명 밑으로 떨어지면 **머리 위에 "선택함" 불만 켜지고 방향은 감춰진다.** 혼자 판단해야 한다.
정답 공개 순간에야 전원이 갈라진다.

임계값은 `TALLY_FROM` 환경변수로 바꾼다.

> **처음엔 100으로 뒀다가 30으로 낮췄다.** 100이면 1~2문항 만에 그 밑으로 떨어져서
> 사람들이 달려가는 간판 연출이 초반에만 보이고 나머지 내내 정지 화면이 된다.
> 30이면 마지막 한두 문항만 깜깜이가 되어 "외로운 결승"이라는 원래 의도는 살면서
> 군중이 갈라지는 장면은 게임 내내 볼 수 있다.

> 이 가리기는 **서버에서** 한다. 클라이언트에서만 숨기면 개발자도구로 그대로 보인다.
> 상품이 걸린 게임이라 타협할 수 없는 지점이다.

### 본부 색

14개 부서를 각각 색으로 나누면 전광판에서 읽히지 않는다. 상위 조직 5개 + 기타로 묶어 6색을 쓴다.
부서명은 카메라가 가까워지는 구간에서 텍스트로 나온다.
조직 이름과 색은 `data/employees.json`의 `divisions`·`departments`만 고치면 되고 코드는 건드릴 필요가 없다.

### 중계

진행 상황을 자막으로 띄우고 동시에 읽는다. **자막이 먼저고 음성이 나중이다** —
소리가 안 나는 환경에서도 진행이 끊기면 안 되기 때문이다.

무엇을 말하는가:

- 문항 시작과 난이도
- 정답, 탈락 인원, 몇 층으로 올라가는지
- **룰이 바뀌는 지점** — 생존자가 임계값 아래로 떨어져 남의 선택이 보이지 않게 될 때
- **10명 이하가 되면 본부별 판세** — "시스템 2명, 지능 2명, 경영 1명. 2명씩으로 팽팽합니다."
- VIP 탈락, 결승 진입, 챔피언

전광판 우측에는 본부별 생존자가 실시간으로 정렬되어 표시된다. 선두 본부는 앰버로 강조된다.

### 소리

효과음은 음원 파일도 네트워크 요청도 없이 전부 런타임에 합성한다. 나레이션은 브라우저
내장 음성 합성을 쓴다. 말이 나가는 동안에는 배경음악을 눌러 둔다(`Music.duck`) ——
마지막 문항은 우승곡 위에서 진행되므로 더킹이 없으면 중계가 곡에 통째로 묻힌다.
문항 시작·서든데스 개시에 울리던 징은 걷어냈다: 음악과 나레이션이 이미 그 자리를 채운다.

**전광판은 첫 클릭이 필요하다.** 브라우저는 사용자가 누르기 전에 소리를 못 내는데
전광판은 띄워놓기만 하니 클릭할 일이 없다. 그래서 준비 화면의 버튼을 한 번 눌러야 한다.
운영자가 회차 전에 한 번 눌러두면 된다. 참여자 화면은 입장할 때 자동으로 풀리고,
대기실 하단의 토글로 끌 수 있다.

> 음성 합성은 함정이 많다. 음성 목록이 비동기로 로드되어 첫 호출에서는 비어 있고,
> utterance 참조를 놓으면 말하다 잘리고, Chrome은 긴 문장에서 스스로 멈춘다.
> `sfx.js`가 이 세 가지를 모두 처리한다.

### 타이밍

| 구간 | 시간 |
|---|---|
| 응답 | 10초 |
| 정답 공개 | 6초 (100명 이상) → 9초 (10명 이하) |
| 부활권 선택 | 4초 |
| 서든데스 | 20초 |

처음엔 응답을 7초로 잡았는데 **문제를 읽고, 남들이 어디로 가는지 보고, 마음을 정할 틈이 없었다.**
후반으로 갈수록 정답 공개가 길어지는 것은 층 상승 연출과 중계 멘트가 들어갈 자리를 만들기 위해서다.
`QUESTION_MS` 환경변수로 조절한다.

### 설계 판단

**WebSocket이 아니라 SSE + POST.** 이 게임은 실시간 액션이 아니라 방송형 동기 게임이다.
전원이 같은 문제를 동시에 받고, 7초 안에 한 글자를 보내고, 결과를 함께 받는다.
양방향 채널이 필요 없으므로 단방향 SSE로 방송하고 답안은 평범한 POST로 받는다.
구현이 단순해지는 만큼 시연 당일 실패 확률이 낮아진다.

**서버는 권위를 가지고, 클라이언트는 렌더링만 한다.** 탈락 판정은 전부 서버가 하고
클라이언트는 결과를 그린다. 화면 효과가 상태를 결정하는 일이 없다.

**답안은 재시도한다.** 네트워크 순간 장애로 답안이 유실되면 그 사람은 틀려서가 아니라
회선 때문에 탈락한다. 이 게임에서 가장 나쁜 버그이므로, 응답 창이 열려 있는 동안 재시도하고
도달 여부를 화면에 표시한다. 버튼이 눌린 것과 서버가 받은 것은 다르다.

**끊긴 참여자는 정리한다.** 그러지 않으면 폰을 닫은 사람이 영구히 참가자로 집계되어
참여율 지표가 오염된다. 단 진행 중에는 정리하지 않는다. 재접속하면 생존 상태를 이어받아야 한다.

**단일 인스턴스로 간다.** 인스턴스를 늘리면 세션 고정과 공유 상태가 필요해져 복잡도만 오른다.
450명 규모에서는 서버 한 대가 정답이다.

## 아직 만들지 않은 것

| 항목 | 상태 |
|---|---|
| **문제 자동 출제 파이프라인** | 별도 논의 후 착수. 현재는 `data/questions.json`에서 읽는다 |
| 사내 SSO 연동 | 현재는 사번 조회만. 상품이 걸린 운영에는 SSO가 필요하다 |
| 시즌 포인트 영속화 | 현재는 회차 내에서만 계산하고 저장하지 않는다 |
| 부서 랭킹 대시보드 | 데이터 축적 이후 |
| 지난 회차 아카이브 | 주 1회 편성의 공백 6일을 메우는 장치 |

파이프라인은 `data/questions.json`의 스키마만 맞추면 그대로 연결된다.
문항마다 `evidence`(근거 원문 문장)를 요구하도록 되어 있고, 이 값이 없는 문항은
파이프라인 단계에서 폐기하는 것이 할루시네이션 차단의 핵심이다.
